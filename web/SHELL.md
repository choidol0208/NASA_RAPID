## Model indicator (15 November, about 17:40 KST; the lead's request of 17:22)

A small, quiet line that names the model that answers here, or says that none does, in the manner of a chat application that names its model under the message box. `shell.js` builds it (`#model-chip`, a link to `how.html#ai-use` that keeps `?q=`); `shell.css` styles it ("the model indicator" block); `assistant.js` reports its mode with the event `fee-model` on `document` (also kept in `window.feeModel`) whenever `setMode` runs. Every name and date comes from the local server's `GET /api/health` reply or from the recorded file; none is written into the shell.

- **Where:** on the start page, its own line right under the input box at its right end (`.ask-meta`, before "Rough input is fine"); once a query is shown, at the right end of the app bar's search form, after the search and copy buttons, so it is in view while a visitor types there at any scroll position. In the app bar only the first part is shown (on a phone only "gpt-oss:20b" or "Rule-based"); the second part is in the title and the accessible name.
- **Live** (health `mode: "live"`): a filled dot, "gpt-oss:20b · local model", second part "Runs on this computer through Ollama"; the title gives the maker, the licence and the digest from the health reply.
- **Local server without a model** (`mode: "no_model"`): a hollow dot, "Rule-based mode", second part "Answers put together by team code from the facts" and, when the reply gives a reason, that reason in plain words (for example "model calls switched off for this run", "the model server did not answer"); the exact reason is in the title.
- **Public page or a static copy:** "Rule-based mode"; with recorded answers, second part "Recorded answers of gpt-oss:20b, 15 November 2026" (model and date from `assistant/recorded.json`); without them, "Dashboard computed by team code". A page without the assistant shows this state on `load`.
- **Changes:** `assistant.js` reads health again when the page comes back into view, after each answer and once a minute while the page is in view; a changed mode or reason updates the section and the indicator.
- **No jump:** the line is in the layout from the first paint with its height kept (`visibility: hidden` until the mode is known). Measured layout shift from it in headless Chrome: 0.012 or less per page.
- **Not on `how.html`** (that page has no input). Hidden in print.

## Tab map

| Tab (`?tab=`) | Sections |
|---|---|
| Closest investigations (`closest`) | `#read`, `#top` |
| What was found (`found`) | `#results-first` (the ui role's section "What NASA's experiments and documents report", shown first in this tab), `#needs`, `#tests`, `#answers`, `#shown`, `#criteria` |
| Where the data are (`data`) | `#piles` |
| Where the evidence stops (`stops`) | `#stops` |
| All investigations (`all`) | `#all` |

`#status`, `#glance`, `#assistant` and `#how` are outside the tabs. A tab whose sections are all hidden is not offered. An address with `#<id>` (a section, or anything inside one, for example `#compare`) opens the tab that holds it and scrolls there at once; the shell keeps the target in place for up to 8 s while `app.js` renders content above it, and lets go when the visitor scrolls, clicks or types. `?tab=<name>` opens a tab; the back button steps through tabs; a tab click while scrolled down (and always on a phone) brings the tab bar back under the app bar.

`#compare` is a block inside `#needs`, so it is under "What was found", not "Where the evidence stops": moving it would change the order inside `#needs` (left for the pm to decide).

For scripts (`capture_media.mjs`, the assistant): `window.feeShell.reveal(selector or element)` opens the tab that holds it and scrolls there; for a section this query does not show it opens the first tab; on the start page it first shows the example run that `app.js` has already made (`?q=ISS` is pushed), as the page without the shell showed it. A plain `section.scrollIntoView()` on a section whose tab is closed, or on the start page, does the same (the shell wraps `scrollIntoView` on the tab sections), so the assistant's `#top` fallback and an assistant without the `feeShell` call still work. A submit of `#ask-form` that carries `data-quiet` (the assistant's own) keeps the visitor's tab and scroll position. After a query `#assistant` follows the open tab's sections and comes before the How-it-works strip; on the start page it stays under the input.

`shell.js` keeps the visitor's tab and scroll position when the assistant submits `#ask-form` itself (the dashboard follows an answer that arrives a minute or two after the question): the assistant sets `data-quiet` on the form for that submit, and `newQuery()` then resets nothing.

## Putting a new section into a tab

Either add its id to `TAB_OF` at the top of `shell.js`, or give the section the attribute `data-tab="found"` (or another tab name) in `index.html`. A section that does neither stays visible under every tab, so nothing is hidden by accident. For a place inside a tab other than the document order, add a line next to the `order` rules in `shell.css` ("the input" block).

## Turning the shell off

Remove the two tags marked in the `<head>` of `index.html` (and of `how.html`):

```html
<link rel="stylesheet" href="shell.css">
<script src="shell.js"></script>
```

The page then renders with `style.css` alone: every section visible, one column. The app bar and the footer blocks stay in the markup, unstyled; the method stays on `how.html`. Without JavaScript the shell sets no state, so every section is visible as well.
